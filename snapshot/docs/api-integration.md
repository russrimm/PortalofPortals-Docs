# API Integration Guide

Programmatic and browser-side integration guide for the Portal 360° REST API.

> **Source of truth:** The auto-generated OpenAPI 3.0.3 schema at [`docs/openapi.yaml`](./openapi.yaml) (regenerated by `pnpm run docs:openapi`). For a high-level catalog of business endpoints (Graph, ARM, Power Platform, Dataverse, etc.) see [`API-DOCUMENTATION.md`](./API-DOCUMENTATION.md); for the full per-route quick-reference see [`API-ENDPOINTS-REFERENCE.md`](./API-ENDPOINTS-REFERENCE.md).

---

## 1. Interactive references

Once the dev server is running, the following endpoints are available to any authenticated user. They are served by the application itself and require a valid Portal 360° session cookie:

| Purpose       | Endpoint               | Notes                                                                         |
|---------------|------------------------|-------------------------------------------------------------------------------|
| OpenAPI schema | `GET /api/openapi.json` | JSON OpenAPI 3.0.3. Regenerate with `pnpm run docs:openapi`.                  |
| Swagger UI    | `GET /api/docs`         | Try-it-out enabled. Auto-forwards session cookie + `X-CSRF-Token` (see § 3). |
| ReDoc         | `GET /api/redoc`        | Read-only renderer. Useful for sharing API documentation.                    |

Local URLs (when running `pnpm run dev`):

- <http://localhost:3000/api/openapi.json>
- <http://localhost:3000/api/docs>
- <http://localhost:3000/api/redoc>

The same paths exist in production at your portal's public hostname (for example `https://portal.example.com/api/docs`).

> The HTML for Swagger UI and ReDoc is shipped with a route-scoped Content-Security-Policy that allows the bundle to load from `cdn.jsdelivr.net`. Every other API response keeps the strict portal-wide CSP.

## 2. Authentication model

Portal 360° is a BFF (Backend-for-Frontend). The browser **never** sees access tokens. All API routes require an authenticated session cookie issued by NextAuth v5 after Microsoft Entra ID sign-in.

| Surface                              | Auth mechanism                                                            |
|--------------------------------------|---------------------------------------------------------------------------|
| First-party browser session (you)    | HttpOnly session cookie + (for mutations) CSRF cookie / `X-CSRF-Token`    |
| Out-of-process automation            | Not supported with cookies — see § 6 for the recommended approach         |
| Public endpoints                     | `/api/auth/**` and `/api/health/**` only                                  |

Every other route returns `401 Unauthorized` if there is no session and `403 Forbidden` if a CSRF check fails on a mutating request.

See [`auth-providers.md`](./auth-providers.md) for Entra ID app registration steps and required scopes.

## 3. Same-origin browser calls (the common case)

Portal 360° UI code, Swagger UI, and any first-party JavaScript running on the portal origin can simply use `fetch` with `credentials: 'include'`:

```ts
// Read — no CSRF needed
const res = await fetch('/api/users?top=10', {
  credentials: 'include',
})

// Mutate — CSRF required
const csrfToken = document.cookie
  .split('; ')
  .find((c) => c.startsWith('next-auth.csrf-token=') || c.startsWith('__Host-next-auth.csrf-token='))
  ?.split('=')[1]
  ?.split('|')[0] // NextAuth stores "<token>|<hash>"

await fetch('/api/invite-guest', {
  method: 'POST',
  credentials: 'include',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': csrfToken ?? '',
  },
  body: JSON.stringify({ email: 'guest@contoso.com' }),
})
```

Swagger UI at `/api/docs` does this automatically:

- `withCredentials: true` makes the browser attach the session cookie.
- A built-in `requestInterceptor` reads the (non-HttpOnly) CSRF cookie and forwards it as `X-CSRF-Token` for `POST` / `PUT` / `PATCH` / `DELETE` requests, but **only** when the request target is same-origin.

## 4. Request / response conventions

- **Base path:** `/api/...` — every backend lives under this prefix.
- **Content type:** request and response bodies are JSON unless explicitly noted.
- **Errors:** match the `ErrorResponse` schema in OpenAPI:

  ```json
  { "error": "string-or-boolean", "message": "human-readable", "details": "optional" }
  ```

- **Pagination:** when an upstream API supports it, query parameters such as `top`, `skip`, `$top`, `$skip`, `nextLink`, or `pageToken` are passed through; responses commonly include a `nextLink` or `pageToken` field.
- **Rate limiting:** the middleware enforces a per-IP sliding window (`200/min` authenticated, `20/min` unauthenticated). Exceeding the limit returns `429` with a `Retry-After: 60` header.

### Scoped write freshness and follow-up outcomes

Intune compliance-policy/configuration create, update, delete, and assignment
handlers invalidate their verified caller's list and affected detail prefixes.
User update, User 360 actions, license assignment, and restore invalidate that
caller's user list query variants, affected User 360 aggregate, groups, and licenses.
Other callers and tenants retain their own entries until expiry; this is not a
tenant-wide notification mechanism.

These reads use `src/lib/cache.ts`, not Next.js tag caching. `tags` remain
compatibility-only; `revalidateTag()` does not invalidate this store. Generate
query variants with `scopeCacheKey(prefix, session, params)` rather than embedding
parameters in the prefix. Use `invalidateCacheScope(prefix, session)` after a
confirmed write. Its boolean result confirms whether invalidation was acknowledged.
`invalidateCache(key)` also invalidates the key's prefix/query variants.

The response cache uses revision-fenced publication. Redis reads obtain a scope
revision and writes atomically compare that revision before publishing; a fill
started before acknowledged invalidation cannot repopulate the new revision.
This works across replicas using the same Redis store and cache implementation.
Revisions expire after 24 hours and are recreated with unique values, preventing
old fills from becoming valid after eviction/expiry. Cache payloads are limited
to 1 MB and 24-hour TTL; in-memory entries and in-flight deduplication each have
a 5,000-entry bound. Redis commands have a five-second timeout and do not queue
while disconnected. In-flight requests may still return their original result
to their original caller; invalidation does not cancel a provider request.

Without Redis the guarantee is per process only. When Redis is configured but
unavailable, reads bypass caching rather than using divergent replica-local
fallbacks. Failed invalidation returns `false`: it does **not** establish
cross-replica freshness after Redis recovery. Existing stale entries can remain
until expiry or a later successful invalidation. Coordinated rollout is required
for the new cache namespace; old running application versions do not participate
in the new revision protocol. Caching is not an authorization boundary; handlers
must still authenticate and acquire/authorize delegated identity before warm hits.

The affected policy/detail and user-summary reads accept `Cache-Control: no-cache`
to bypass the BFF cache for an explicit refresh; user lists also support
`nocache=1`. Browser `cache: 'no-store'` alone does not bypass a BFF cache.
The policy and user interfaces use explicit fresh reads and keep failed-refresh
feedback separate from the confirmed mutation outcome.

- A confirmed write can return `refreshRequired: true` if cache invalidation or
  another follow-up failed. `mutationCompleted: true` means the write completed,
  not that the displayed data refreshed or the audit follow-up succeeded.
- A failed post-write follow-up returns HTTP 200 with the completed result and a
  safe `followUpError` containing the error category/status (including consent
  signals when applicable). Do not replay the mutation; refresh/reconcile instead.
- Configuration updates involving multiple provider writes return HTTP 207 with
  `partial: true`, `success: false`, and `completedSteps` if a later step fails.
  Review the current profile before submitting only remaining changes.
- A failed provider write remains a failure and does not invalidate a warm
  successful read as if a change were confirmed. Provider eventual consistency
  is not eliminated by cache eviction.

## 5. CSRF protection in detail

CSRF is enforced in `middleware.ts` for every cookie-authenticated mutating request (`POST`, `PUT`, `PATCH`, `DELETE`) that is **not** under `/api/auth/**` or `/api/health/**`.

The check requires both of the following:

1. The `Origin` (or `Referer`) header matches the resolved auth origin (`AUTH_URL` / `NEXTAUTH_URL`) or the current request origin.
2. The `X-CSRF-Token` header matches the token half (the part before `|`) of the NextAuth CSRF cookie.

If either fails the request is rejected with `403 Invalid CSRF token` and a `reason` field (`missing-origin`, `origin-mismatch`, `missing-token`, `missing-cookie`, or `invalid-token`).

> **Cookie names** — production uses `__Host-next-auth.csrf-token`; non-production uses `next-auth.csrf-token`. If `AUTH_COOKIE_NAMESPACE` is set, the prefix changes to `next-auth-<namespace>`. The `authjs.*` aliases are also accepted.

## 6. Calling the API from outside the browser

Out-of-process clients (CI jobs, scripts, other services) **cannot use the session cookie** — it is HttpOnly and tied to a browser login. For those cases:

- **Preferred:** Call the upstream APIs directly with their native service credentials:
  - Microsoft Graph: app-only token via client credentials flow, scoped to the permissions you need (see [`API-DOCUMENTATION.md`](./API-DOCUMENTATION.md) § Required Permissions).
  - Azure Resource Manager: managed identity or service principal with the appropriate RBAC role.
  - Power Platform / Dataverse: application user provisioned in the target environment.
- **Not supported:** Sharing user session cookies between scripts and a browser. The portal is built around delegated user context and OBO token exchange.

If you need to embed Portal 360° flows in another service, consider extracting the relevant business logic into a dedicated backend service rather than scraping the BFF.

## 7. Regenerating the schema

The OpenAPI document is built by static analysis of every `src/app/api/**/route.{ts,js}` file (see `scripts/generate-openapi.mjs`).

```bash
pnpm run docs:openapi
# Writes docs/openapi.yaml and docs/openapi.json
```

The generator extracts:

- HTTP methods from exported route handlers (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`)
- Path parameters from `[param]` and `[...param]` folder segments
- Query parameters from `URLSearchParams.get(...)` calls
- Request-body fields from the first top-level Zod `z.object({ ... })` in each handler
- Tags from the second path segment (e.g. `/api/azure/...` → `azure`)

The `/api/openapi.json` route serves the JSON copy at runtime, so re-running the generator is all that is required to update Swagger UI and ReDoc.

## 8. Troubleshooting

| Symptom                                                  | Likely cause                                                              | Fix                                                                                                  |
|----------------------------------------------------------|---------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|
| `401 Unauthorized` on every request                      | No session cookie / session expired                                       | Sign in at `/` and retry. Confirm cookies are not blocked.                                           |
| `403 Invalid CSRF token` (`missing-token`)               | `X-CSRF-Token` header not set on a mutating request                       | Read the CSRF cookie and forward it as shown in § 3. Swagger UI does this automatically.             |
| `403 Invalid CSRF token` (`origin-mismatch`)             | `Origin` does not match `AUTH_URL` / `NEXTAUTH_URL`                       | Set `AUTH_URL` to the canonical public URL (or unset to use the request origin).                     |
| `429 Too Many Requests`                                  | Rate-limit exceeded for your IP                                           | Wait the `Retry-After` interval, or run heavy batches with backoff.                                  |
| `500 openapi-schema-missing` on `/api/openapi.json`      | `docs/openapi.json` not present on disk                                   | Run `pnpm run docs:openapi`.                                                                          |
| Swagger UI blank / `Refused to load` errors in console   | CSP for `/api/docs` is being overridden by a proxy or extension           | Confirm middleware exception is in place (see `middleware.ts`). Disable browser extensions and retry. |

See also [`API-AUTH-AUDIT.md`](./API-AUTH-AUDIT.md), [`API-AUTH-QUICK-REFERENCE.md`](./API-AUTH-QUICK-REFERENCE.md), and the wider [`TROUBLESHOOTING.md`](./TROUBLESHOOTING.md).
