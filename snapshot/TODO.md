### Azure SRE Agent Integration (MCP Connector)

Expose Portal 360 as an MCP server that Azure SRE Agent connects to as a
Connector (see [Tutorial: Set up the MCP connector in Azure SRE Agent](https://learn.microsoft.com/en-us/azure/sre-agent/mcp-connector)),
closing SRE Agent's blind spot around Entra/Conditional Access/RBAC/device
config changes (it natively correlates only GitHub deploys, App Insights,
Log Analytics, Resource Graph, and Activity Logs).

**Benefits**
- Correlate infra incidents with tenant config drift (role assignment,
  Conditional Access edits, app credential changes) that SRE Agent can't see today.
- Extend SRE Agent's mitigation reach beyond Azure-CLI-scoped resource groups
  into M365/Entra/Power Platform actions (revoke sessions, restart device),
  gated by Portal 360's own approval framework.
- Unify approvals — route SRE Agent's approve/deny prompts through Portal
  360's existing `approval_policy` / `approval_instance` model into one
  admin approvals inbox.
- Feed Foundry/Power Platform ownership and DLP posture into SRE Agent's
  investigations of AI/Power Platform resource incidents.
- Reverse direction (not via this connector): surface SRE Agent's incident
  investigations in Portal 360's Security queue alongside Defender alerts,
  via SRE Agent's own APIs/webhooks.

**Proposed MCP tool schema** (`portal360-mcp` server)

- Read tools (Tier 0, no approval): `get_user_360`, `list_recent_directory_changes`,
  `get_device_status`, `get_resource_ownership`, `list_security_incidents`.
  Each requires a `correlationId` param; every call writes an `audit_event`
  with `actor = "sre-agent-connector"`, `provider = "mcp"`.
- Write tools (Tier 1, gated): `revoke_user_sessions`, `restart_device`,
  `request_portal_approval` (creates an `approval_instance` so the action
  surfaces in Portal 360's Approvals inbox, not just SRE Agent's own chat
  approve/deny). Each write tool creates an `action_request` row through
  the same path as UI-initiated actions — SRE Agent's approve/deny is a
  second gate, not a replacement. Require `reason`, `sreIncidentId`
  (stored as `upstream_correlation_id`), and `idempotencyKey`.
- Rollout: connect read tools only first and validate in SRE Agent chat;
  add write tools later, scoped to a dedicated `SREAgentResponder` portal
  role, only after `request_portal_approval` exists. 8 tools total against
  the connector's 80-tool budget.

**Hosting**
- New Container App (`portal360-mcp`), same Container Apps environment,
  separate from the interactive BFF — distinct auth surface (OAuth 2.0
  client credentials via a dedicated `portal360-mcp-connector` Entra app
  registration, not user session cookies), independent scaling/blast
  radius, own managed identity with least privilege.
- Calls into existing internal services (Entity Aggregation Service,
  Action Execution Service) over internal Container Apps ingress; no new
  data store.

**Known preview limitation — network design constraint**
- SRE Agent VNet integration is real, but **Connector traffic (Builder >
  Connectors > MCP Server) does not route through the VNet during preview
  — it's public-internet egress only**, and VNet integration is
  egress-only (no inbound private endpoint to the agent). This is
  distinct from the separate "Remote MCP server access" managed-path
  toggle.
- Until this changes: expose `portal360-mcp`'s `/mcp` route publicly but
  locked down — Front Door/App Gateway + WAF in front of the Container
  App, mandatory OAuth 2.0 token validation on every call, optional mTLS,
  and IP allowlisting once Microsoft publishes stable SRE Agent connector
  egress ranges (not published as of this writing).
- Revisit for fully private VNet-to-VNet once SRE Agent connector routing
  reaches GA. Flag to security review before implementation given the
  public-ingress requirement for a tool with write access to directory/device actions.

### P0 - Must Have Gaps (Not Yet Fully Implemented)

**Recommended order for the remaining P0 items** (each is annotated in place below with measured scope, approach, and named risk):

1. **Central API orchestration / provider capability framework** - highest structural value, highest risk. Bound it with a third ratchet instead of a 358-file refactor.
2. **Task-oriented navigation (jobs-first)** - largest effort, lowest technical risk. Validate the taxonomy with real admins on paper first.
3. **Persisted search index** - do last. Blocked on sync-worker/queue infrastructure that does not exist, and a half-built index is a permission-bypass risk whereas today's live fan-out is correct-by-construction.

(The two other open P0 entries - full audit trail coverage, and the deep-link fallback - are respectively ratcheted-and-shrinking and complete.)

- [ ] **Task-oriented navigation model (jobs-first) is missing** - Current navigation remains primarily product-area based. Target: Add job-based top-level flows: Manage User, Reset Access, Assign License, Manage Device, Review Alert, Inspect Mailbox/Teams, Foundry Access.
  - Measured scope: **416 `page.tsx` files**, **438 entries** in `src/lib/route-registry.ts`, and the product-area tree in `src/app/graph-explorer/nav-areas.ts` (867 lines). This is the **largest** of the remaining P0 items by effort and the **lowest** by technical risk - it is additive surface area, not a rewrite of behavior.
  - Recommended approach: add a job layer **alongside** the existing product-area tree rather than replacing it. Every job is a curated composition of pages and actions that already exist, so the underlying routes, guards, and audit records are untouched. Keep the product-area tree as the escape hatch for anything a job does not cover.
  - Named risk: the failure mode here is **building the wrong taxonomy**, not breaking the app. A job list invented from the spec will not survive contact with real operators. Validate the taxonomy on paper with actual admins - which jobs, in what order, with which steps - **before** writing code, because the cost of relabelling 400+ pages twice is the entire budget of this item.
  - Prerequisite worth doing first: the registry already knows every route's title and parent, so a `job` tag on `RouteConfig` is the cheapest possible way to express membership and would let a job view be assembled by query rather than by a second hand-maintained tree that can drift out of sync.

- [x] **Universal global entity search is implemented** - `/api/search/global` fans out across users, groups, devices, alerts, roles, licenses, mailboxes, Power Platform environments, Foundry resources, registered pages, and quick actions, and ranks the merged result set.
  - Environment results come from the Power Platform BAP admin API (they previously returned Intune managed devices, mislabelled as environments).
  - Alerts now read `security/alerts_v2` rather than the deprecated `security/alerts`. `alerts_v2` supports only `$count`/`$filter`/`$skip`/`$top` — no `$select`, no `$orderby` — and returns newest-first, so the query was adjusted accordingly and its lowercase severity/status values are title-cased for display.

  - Results are emitted **clustered by type**, groups ordered by their best-scoring member. The command palette renders grouped but drove keyboard navigation from the flat array, so a globally interleaved sort would have desynced arrow-key order from visual order; the palette now derives its navigation order from the rendered grouping so the two cannot diverge.

- [ ] **No persisted search index - global search is a live fan-out** - `/api/search/global` (552 lines) fans out on every keystroke-driven query across 7 Microsoft Graph endpoints plus Azure Resource Graph via `Promise.allSettled`. This works, but latency and throttling exposure scale with tenant size and with the number of concurrent admins, and it cannot satisfy the spec's tier-4 "relationship relevance to recently viewed items" because there is nothing persisted to rank against.
  - Blocking prerequisite: this needs **sync-worker and job-queue infrastructure that does not exist yet**. Cosmos and Redis are both already present and wired up, but there are **no sync workers and no queue**, so this item is substantially larger than it appears - the index is the small part.
  - **Named security risk, and the reason this must be designed rather than bolted on:** a persisted index is a **permission-bypass vector**. Results cached from one admin's delegated fan-out must never be served to another admin who lacks access to those objects. Read-time re-authorization (filter results against the *current* caller's permissions at query time, never trust what was indexed) has to be in the design from the first commit; retrofitting it means auditing every read path afterwards.
  - Recommended ordering: this is the **last** of the three remaining P0 items. Live fan-out is correct-by-construction today, so the current state is safe but slow - whereas a half-built index is unsafe. Do not start it until the provider client above exists, since the sync workers should consume that client rather than adding a 359th bespoke fetch pattern.
